## 固定输入、几何与证据口径

每例都是独立新进程、一个不可重放的计划。初始正文为既有 78 字节合成源，SHA-256 `c7dd4a7fa283dd0003ca8b2ae13dcb46f143a4717bf5a14eb5f5acb068a9fa1c`。阶段 0 写正文；阶段 1 仅缩窄并采 DSR；阶段 2 单独准备并采 DSR，必须确认旧尾部仍在；随后才释放编辑字节。最终恢复宽度时只采 DSR，不重绘正文。

实际窗口 `1360×749 → 1000×749 → 1360×749`，实际 NAWS `91×20 → 61×20 → 91×20`；中间动作阶段始终保持 61×20。Windows VM `10.0.26300`，WindTerm 2.7.0 x64，REA `6.7.0`，Python `3.12.10`。这是直接 Telnet 原版证据，不是正式 Qt / 固定 ConPTY 联合验收。

下文 DSR 使用一基协议坐标；文档行列使用零基；矩形为像素 `(x,y)`。API `position`、文档行列、显示矩形与协议光标分别记录，不互相替代。`ANCHOR` 内本来有一个 `R`，位于文档 `(2,5)`、position `17`；下文“新增 R”专指编辑阶段产生的另一个字符。

三份严格导出逐项核验固定输入及全部动作前观察、NAWS/DSR、实际几何、生成 probe、provider evidence ID、源码归档、完整 4047 文件原包与模块、合成 profile、一次 attempt 和回收记录。归档前再次检查精确公开 schema、禁止私有字段/路径、源文件 SHA，并按原字节复制。公开材料只有合成输入、marker/DSR/几何、摘要和标量，没有原文全文、本地路径、PID、会话、profile 或原版资源。三份 JSON 均为 `job_after.active=0`；主动终止进程不等于证明原版自然退出。

## Q 与 R：Q 当次已经移除所观察到的旧尾部

| 1：缩窄 | 空；另发 DSR | `11;2` | `v` 文档位置不变，显示 `(379,144)` |
| 2：准备 | `1b5b383b363148`，即 `CUP(8,61)` | `8;61` | 正文与阶段 1 相同，`v` 仍在 |
| 3：首次写新右界 | `51`，即 `Q` | `8;61` | `Q=(7,60)`，position `83`，显示 `(627,126)`；**v 已消失** |
| 4：下一个字符 | `52`，即 `R` | `9;2` | 新增 `R=(7,61)`，position `84`，显示 `(147,144)`；逻辑文本中紧接 Q |

## ICH1 与 DCH1：保留 61 个空格，旧 v 不复活

两例均单独准备 `CUP(8,61)`；准备完成时 `v` 仍在文档 `(7,90)`，正文与缩窄前的保留文本一致。随后分别发送 `1b5b3140`（ICH1）或 `1b5b3150`（DCH1）。

| 观测 | ICH1 | DCH1 |
|---|---|---|
| 五阶段 DSR | `11;2 → 11;2 → 8;61 → 8;61 → 8;61` | 相同 |
| 编辑后文档行 7 | 61 个空格 | 61 个空格 |
| 旧 v | 编辑后消失，恢复宽度后未复活 | 相同 |
| w/x 文档行列 | 仍为 `(9,90)/(9,91)` | 相同 |
| w/x 全局 position | `206/207 → 176/177` | 相同 |
| 编辑后窄屏 w/x 矩形 | `(379,180)/(387,180)` | 相同 |
| 恢复后 w/x 矩形 | `(867,162)/(147,180)` | 相同 |
| 文档行数 | `11→12→12→11→11` | 相同 |

这里不是仅凭缺失 v 或 position 差值推算空白长度：将原始合成文档唯一修改为“行 7 是 61 个空格”，独立计算整组文档规范 JSON SHA-256，得到 `72ce14cfd467f2304d1f7909b88d2f2c3df760408bf15b98c5183fb7af1d13ca`，精确匹配两例编辑后与恢复后的四个公开摘要。所观察到的文档空白 extent 为 61；它不等于原版内部 `Cell.written`、显式输入空格或复制策略。

## EL0 准备失败与 EL2 未运行

`erase-right` 在窄屏阶段 2 执行 `CUP(8,1), L, CUP(8,61)`，准确字节为 `1b5b383b31484c1b5b383b363148`。其前置条件要求只增加左侧 L，同时保留旧 v；实际记录为 `status=failed`、错误 `Error: preparation changed source beyond declared prefix`，仅采集了阶段 0/1/2，未释放 EL0 动作。

以下是**尚未经过完整严格失败导出的原始观察**，与上面三份严格结果分列：阶段 2 的 DSR 为 `8;61`；文档行 7 确为 `L + 60 个空格`，长度 61；L 在 `(7,0)`、position `23`、矩形 `(147,126)`，旧 v 已消失；`w/x` 仍在文档行 9，但 position 降至 `176/177`，文档行数由 12 降至 11。这提示裁尾并非只在新右边界 Q 上出现：窄屏列 0 的普通写入也产生了该原始结果。它不是 EL0 语义通过，也没有恢复阶段结果可供本例比较。

失败计划 SHA-256 为 `a2594faf4528f45592458e78441249eb702c7449cfb2466bb849b79ea5f51c81`；本地原始结果文件 SHA-256 为 `2ed2414fbc5e5bcd5fc1e02d86d5df820d48293ad87646cb723102edb06bae0d`。这里只发布失败身份与固定合成内容摘要，不复制 raw JSON，不改变原失败状态，也不补造严格成功记录。

`erase-whole-line` 使用相同的窄屏写 L 准备方式，因前置条件已知不成立而未运行，原版运行次数为 0。后续 EL0/EL2 必须使用独立新源码和计划：在初始 91 列正文中预先放好 L，再缩窄，准备阶段只定位。不能重放旧失败计划，不能用删掉 L 对照或忽略尾部丢失来宣称本批擦除通过。

## 对同 owner 实现的约束与尚未覆盖的行为

可与严格观测相容的工程合同是：纯宽度变化保留原源片段；对已测目标行执行 Q、ICH1、DCH1 时，将该行发布为当前 61 列的内容范围；Q 后的下一 R 使用新 61 列边界形成真实软续接，逻辑顺序为 Q、R。未编辑的 `w/x` 继续保留其旧正文。单纯保留 91 列源片段并让原 `put/ICH/DCH` 修改前 61 列、留下旧 v 的实现，与这些结果不符。

“编辑前收敛源片段到当前宽度”是 TermForge 可以采用的实现方式；本证据不能区分原版内部先裁后编辑、先编辑后裁或其他机制。源 ID、rank、epoch 与内容版本如何发布也由 TermForge 的工程不变量约束，不是从原版文档 API 读取的内部事实。空白 extent 应能与纯容量 padding 区分，不能为了保留 61 空格而把擦除/插删产生的空白伪装成用户显式写入；具体元数据名称不代表原版存在相同成员。

本批仍未验证 EL0/EL2、任意内部列写入、多个插删位置/数量、其他尺寸、超出新宽度的旧光标、宽字/结合字、样式、margin/origin、主/备用帧交叉、高度变化、历史淘汰与在途输出；普通列 0 写入目前只有上述准备失败原始观察。文档保留 61 个空格也不证明复制这些空白或再缩至更窄时的完整行为。正式 Qt 默认行为、固定 ConPTY 传输及产品验收不能从这组直接 Telnet 结果推导。
