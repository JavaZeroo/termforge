# WindTerm 2.7.0：Unicode 缩宽、后续输入与位置单位

本报告归档 [固定 Unicode 协议](../../resize_unicode_reference.md)的 **2 次独立原版运行、8 个阶段**。两例均只运行一次，原机械审计、严格导出及受控回收通过。固定 WindTerm 2.7.0 x64，Windows VM `10.0.26300`，Python `3.12.10`，REA `6.7.0`；实际 NAWS `91×20 → 61×20 → 91×20`，高度不变。

**正文与 DSR 的变化已经明确；Unicode 后续字符的矩形仍是特定 API 数值查询结果，不能直接当作字形或 C++ Cell 位置。** 本组全为 BMP 字符，也不足以区分通用 UTF-16 与 Unicode scalar API 单位。

## 精确正文：宽字边界

公共前缀设置 origin OFF、wrap ON、全屏 margin、SGR0、ED2，然后写数字与 ANCHOR 锚点。阶段 0 于 `CUP(8,61)` 写 UTF-8 `界Z`（hex `e7958c5a`）。阶段 1 只缩宽并发 DSR；阶段 2 仅写 Q；阶段 3 只恢复宽度。每个阶段独立采样。

以下 DSR 一基；文档行零基。令 P 为固定前七行 `["", "0123456789", "ANCHOR", "", "", "", ""]`，`S60` 为精确 60 个 ASCII 空格。

| 阶段 | DSR | 完整文档数组 | 第 7 行 UTF-8 字节 / scalar / UTF-16 数 |
|---|---|---|---|
| 0：初始 | `8;64` | `P + [S60 + "界Z"]` | `64 / 62 / 62` |
| 1：仅缩宽 | `8;61` | `P + [S60 + "界Z", ""]` | `64 / 62 / 62` |
| 2：仅写 Q | `8;61` | `P + [S60 + "Q"]` | `61 / 61 / 61` |
| 3：仅恢复 | `8;61` | 与阶段 2 完全相同 | `61 / 61 / 61` |

缩宽前后 `界Z` 的源文本均保留，变化是一条末端空文档行及 DSR 限制到第 61 列。写 Q 后 `界Z` 消失，末行变为 60 空格加 Q；恢复宽度不复活旧文本。文档行数 `8→9→8→8`，`scroll=0`、capacity 20 始终不变。

`lineStart(7)` 返回 23。界前的 60 个字符全是 ASCII，因此它的 UTF-8、UTF-16、scalar 三种前缀长度均为 60，实际查询数值均为 **83**；这一查询起点没有三者之间的偏移歧义。其矩形从 `(627,126,13,18)` 移到 `(147,144,13,18)`，即下一显示行起点附近。Q 的查询也是 83，阶段 2/3 矩形为 `(627,126,8,18)`。这些支持本例界的起点随窄屏布局移到下一显示行；没有检查整个字形像素是否完整，也不能把矩形宽 13 当成 13/8 个 terminal cell。

**Z 不能使用相同解释。** 它的 scalar/UTF-16 前缀为 61，UTF-8 前缀为 63。冻结采样查询了 `23+61=84`，没有查询 UTF-8 候选位置 86。该查询矩形初始为 `(627,126,21,18)`，缩宽为 `(147,144,21,18)`，与界共享 x/y；这不证明 Z 在界的起点，也不证明两个 terminal cell 重叠。

## 精确正文：结合标边界

阶段 0 在同一个 `CUP(8,61)` 写 `e\u0301Z`（UTF-8 hex `65cc815a`，没有把 NFD 输入转成 NFC）。阶段 1 只缩宽；阶段 2 仅输入 U+0302（hex `cc82`），中间没有 CUP；阶段 3 只恢复。

| 阶段 | DSR | 完整文档数组 | 第 7 行 UTF-8 字节 / scalar / UTF-16 数 |
|---|---|---|---|
| 0：初始 | `8;63` | `P + [S60 + "e\u0301Z"]` | `64 / 63 / 63` |
| 1：仅缩宽 | `8;61` | `P + [S60 + "e\u0301Z", ""]` | `64 / 63 / 63` |
| 2：仅追加 U+0302 | `8;61` | `P + [S60 + "\u0302e\u0301"]` | `65 / 63 / 63` |
| 3：仅恢复 | `8;61` | 与阶段 2 完全相同 | `65 / 63 / 63` |

阶段 2/3 的精确非空后缀是 **`cc8265cc81`**：U+0302 位于 e 之前，原 U+0301 仍在 e 之后，Z 消失。不能将它误写成 `e\u0301\u0302`、`e\u0301Z\u0302` 或 NFC 预组合字符。正文 SHA 为 `f585595566948a83a6c1b172e9d1c8a0830e6e9cb62ca80dfcbfbb18b17372a6`。文档行数同样 `8→9→8→8`，scroll 与 capacity 不变。

下表完整列出本例非 ASCII 区域的实际查询，所有矩形格式都是 `(x,y,width,height)`；“文本偏移”不是 Cell 列。

| 阶段 | 标签 | scalar/UTF-16 偏移 | UTF-8 前缀字节 | 实际查询 `23 + 文本偏移` | 查询返回矩形 |
|---|---|---:|---:|---:|---|
| 0/1 | e | 60 | 60 | 83 | `(627,126,8,18)` |
| 0/1 | U+0301 | 61 | 61 | 84 | `(635,126,8,18)` |
| 0/1 | Z | 62 | 63 | 85 | `(635,126,16,18)` |
| 2/3 | U+0302 | 60 | 60 | 83 | `(627,126,8,18)` |
| 2/3 | e | 61 | 62 | 84 | `(627,126,16,18)` |
| 2/3 | U+0301 | 62 | 63 | 85 | `(635,126,8,18)` |

这些矩形是原接口对已记录数值的回答；后续字符的 UTF-8 与文本偏移已经分离，不能把表中的“e 查询”或“Z 查询”直接升级为字形位置/附着关系。U+0302 出现在原文档的 e 之前，是正文事实；它是否附着到前一个空白 Cell、以孤立标记存储，或受其他暂态影响，仍需区分。

## 位置单位线索与实现边界

两例阶段 0 的 `caretPosition` 都为 87，而 `lineStart(7)=23`、该行 UTF-8 长度都为 64；`23+64=87`。相应 scalar 行长却分别为 62/63。结合标阶段 2 的 caretPosition 为 85，也与查询起点 83 加新 U+0302 的两个 UTF-8 字节相容。**这些是 API 可能按 UTF-8 字节计量的线索，未完成一般单位校准；不能反向修改已冻结采样或将所有位置字段重解释为字节。** 所有输入均为 BMP，进一步区分 UTF-16 与 scalar 还需要不同样本。

目前可直接建立字面回归的是固定输入、每阶段 DSR、完整合成正文及 ASCII 锚点，界的纯 ASCII 前缀起点也可有限比较。保留正文的显示映射需要继续遵守不同单位分列；不能从本组 API 查询宽度推导 C++ wide continuation cell 宽度。

结合标结果不能立即变成“resize 后一律产生孤立 mark”的政策：本例同时存在初始 DSR、缩宽后的 DSR、光标从第 63 列限制到第 61 列，以及后续 U+0302 输入。尚未区分纯 DSR、resize 本身、列限制或已有附着状态。需要新独立小样本，先校准 UTF-8/文本偏移候选查询，再比较连续输入、无 resize 的 DSR 间隔、保持光标列不变的 resize，以及空白位置的 mark 前后结果；不重放旧计划。

本组没有高度改变、宽度 1、非 BMP 字符、emoji/ZWJ、其他字体/字宽、样式、任意尺寸、完整像素/active grid、历史淘汰、在途输出或可靠性重复。它不是正式 Qt/fixed-ConPTY 联合验收、性能结果、完整 Unicode 对齐或 R2 完成声明。
