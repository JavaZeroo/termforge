# WindTerm 2.7.0：中间列 EL0 / EL2 的正文终点

本报告记录 [CUP(8,31) 独立协议](../../resize_erase_interior_reference.md)的实际结果：**两例各一个新进程、五阶段，原机械审计和严格导出均通过；本批共 2 次原版、10 阶段。** 同样的 61 列网格中，EL0/EL2 后文档目标行长度均为 30；与此前 CUP(8,61) 的长度 60 对照，可排除这组固定源始终取“宽度减一”的解释。

上述结果只说明被测文本在两个定位点的文档终点随光标前缀变化，不证明完整 active grid、任意光标列或原版内部擦除算法。[先前末列两例](../2026-11-02-resize-erase-reference/README.md)仍是“原审计失败后独立离线补充通过”，不倒填为原 strict，也不合并到本批成功计数。

| case | 动作 | 本批结果 | 公开文件 |
|---|---|---|---|
| `erase-right` | EL0，`1b5b304b` | 1 次新进程，5 阶段，原审计及严格导出通过 | [erase-right.json](erase-right.json) |
| `erase-whole-line` | EL2，`1b5b324b` | 1 次新进程，5 阶段，原审计及严格导出通过 | [erase-whole-line.json](erase-whole-line.json) |

## 单变量输入、环境和审计边界

初始正文仍为同一 **85 B** 合成源，SHA-256 `a301c656926ae72c07d2c91b67e1734286ce50b7cb38c5b4f6b64f06db0563b3`。它由既有 78 B 加入 7 B 的 `CUP(8,1), L` 得到；L 在初始 91 列时写入，缩窄后不再打印 L。与先前 85 B 末列协议相比，本次行为变量是阶段 2 的准备从 `CUP(8,61)` 改为 **`CUP(8,31)`**，hex `1b5b383b333148`。两组使用不同 source/schema/plan/attempt，不是旧失败重放。

实际环境为 WindTerm 2.7.0 x64、Windows VM `10.0.26300`、REA `6.7.0`、Python `3.12.10`。每例都是独立新进程和合成 loopback Telnet 会话；窗口 `1360×749 → 1000×749 → 1360×749`，NAWS `91×20 → 61×20 → 91×20`。动作阶段维持 61×20；每阶段只追加一次 `ESC[6n`，不补绘或纠正光标。

阶段 1 与阶段 2 的完整文档数组相同，阶段 2 回复 `8;31`，所以两个 case 均在不改变正文的 CUP 前置完成后才发送 EL。阶段 3/4 的有限发布集合同时允许长度 `0/30/60/61/91` 的源派生结果及原有有限文本；它没有把长度 30 写成语义通过条件。返回不同可解释结果也会记录，任意私有文本、未知字符、超界 padding 或重复 marker 则拒绝。

严格导出核验每个新计划的外部 SHA、固定输入与完整阶段、NAWS/DSR/窗口、provider evidence ID、生成脚本、源码归档、完整 4047 文件原包、加载模块、合成 profile、一次 attempt 及回收。归档前再核精确公开 schema、来源与脱敏，独立重建全部合成文档数组确认 SHA 后，才按原字节复制。没有发布文档全文、本地路径、PID、用户会话、profile 或原版资源。两份 JSON 的 `job_after.active=0`；主动终止后 Job 空不证明自然 GUI 退出。

## 五阶段的直接观察

DSR 是一基协议坐标，文档行列从零开始，矩形为像素 `(x,y)`。文档 `line_count`、position 与可见矩形保持独立记录，不用它们反推协议网格。

| 阶段 | 输入本体 | 两例 DSR | 共同观察 |
|---|---|---|---|
| 0 | 固定 85 B 正文 | `11;2` | L `(7,0)`、v `(7,90)`；w/x `(9,90)/(9,91)` |
| 1 | 空，仅缩窄 | `11;2` | 文档坐标保持；v/w/x 可见位置重排 |
| 2 | `CUP(8,31)` | `8;31` | 文档与阶段 1 完全相同；L/v 仍在 |
| 3 | 各自 EL0 或 EL2 | `8;31` | v 消失；EL0 保留 L，EL2 清除 L；w/x 保留 |
| 4 | 空，仅恢复宽度 | `8;31` | 已消失的 L/v 未复活；其余文档位置保持 |

| 观测 | EL0 | EL2 |
|---|---|---|
| 阶段 3/4 的文档行 7 | `L + 29 个空格`，总长 **30** | **30 个空格** |
| L | `(7,0)`、position `23`，矩形 `(147,126)` | 擦除后消失 |
| v | 擦除后消失，恢复未复活 | 相同 |
| w/x 文档坐标 | `(9,90)/(9,91)`，不变 | 相同 |
| w/x position | `206/207 → 145/146`，减少 61 | 相同 |
| 擦除后窄屏 w/x 矩形 | `(379,180)/(387,180)` | 相同 |
| 恢复后 w/x 矩形 | `(867,162)/(147,180)` | 相同 |
| 文档行数 | `11→12→12→11→11` | 相同 |
| 文档 scroll | 五阶段均 0 | 相同 |

全部阶段的 ANCHOR 保持文档 `(2,0)`、position `12`、矩形 `(147,36)`。v 初始矩形为 `(867,126)`，缩窄与 CUP 后为 `(379,144)`；w/x 在擦除前的窄屏矩形为 `(379,198)/(387,198)`。后续 marker 上移一显示行与目标长行的正文变化同时出现，但这不是 source owner/ID 迁移的观测。

## 完整合成正文的独立核对

按固定 85 B 源构造文档数组：初始行 7 为 `L + 89 空格 + v`，行 9 为 `90 空格 + wx`；缩窄及 CUP 阶段保持源文本，并包含已观察的尾部空文档行。擦除后仅把行 7 替换为上表各自的 30 字符结果。以规范 JSON 编码重算 SHA，**两例全部 10 阶段都与公开 `synthetic_lines_sha256` 一致**；不是只凭 marker 消失或 position 差值估计空格数量。

## 与末列样本对照及工程边界

| 对照项 | 先前末列，CUP(8,61) | 本批中间列，CUP(8,31) |
|---|---|---|
| 擦除时网格 | 61×20 | 61×20 |
| 初始正文 | 同一 85 B | 同一 85 B |
| EL0 后文档行 7 | `L + 59 空格`，长 60 | `L + 29 空格`，长 30 |
| EL2 后文档行 7 | 60 空格 | 30 空格 |
| w/x 后续 position | 175/176 | 145/146 |
| 来源状态 | 两原审计失败，独立离线补充通过 | 两原机械审计及严格导出通过 |

两个位置都与零基光标列之前的前缀长度一致，因此本组不支持无条件取 `current_width - 1` 的工程规则。若 TermForge 以现有 source owner 保存正文与有效范围，应以这两个独立字面样本约束 EL0/EL2 的结果，同时保留 61 列网格容量与文档内容范围的区别；具体元数据和发布时机是独立实现选择。

这并不证明原版内部用“光标前缀长度”作为统一算法，也没有验证所有第 31..61 列 Cell 的空白属性。EL2 保留 30 个空格可能涉及文档表达或其他内部机制；这组公开 API 不能区分。其他光标列、宽度、非 resize 擦除、连续编辑、擦除后下一字符、宽字/组合字符、样式、带背景空白、软续接、主/备用交叉及高度变化仍需各自合同。不得把有限 ASCII 文档观察扩大为完整 active grid、完整擦除实现或所有平台行为匹配。

本报告不合并旧失败、补充审计、帧测试或 C++ 测试计数，也不构成正式 Qt/固定 ConPTY 联合验收、可靠性重复、性能等价或 R2 完成声明。
