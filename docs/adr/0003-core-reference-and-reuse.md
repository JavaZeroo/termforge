# ADR-0003：差分参考与可重审的核心路线

> 本文保留 C1/G1 等旧代号和当时的比较结果。2026-10-25 已由 [#20](https://github.com/JavaZeroo/termforge/issues/20)/[#26](https://github.com/JavaZeroo/termforge/issues/26) 完成 R2 重审；现状见 [FEATURES](../FEATURES.md)。

- 日期：2026-10-22；重审：2026-10-25
- 状态：已接受 R2 复用候选核心的路线；产品整合尚未验收
- 对应任务：C1；R2-00 至 R2-03

## 问题

现有自研核心已经能回放有限文本、样式和历史，但单靠自己写预期容易把实现行为误当协议。若继续逐项扩展到完整终端，错误恢复、模式交互、Unicode、resize 和应用兼容性的维护成本会增长。完整开源允许复用开源核心；语言本身不构成性能证据。

## 已运行的比较

使用固定 **pyte 0.8.2 / wcwidth 0.2.13** 作为无界面语义参考，依赖、许可、哈希和入口见 [差分实验](../../experiments/differential/README.md)。同一套 19 场景、5 种分块、1011 个检查点同时驱动独立 C++ 核心与 Python 参考：13 场景一致，6 个边界场景存在可重复差异。所有观察保留输入与状态，另有中途不一致但最终恢复的回归。

这证明适配接口和差分方法已可使用，也证明 pyte 不能直接被当作全覆盖真值。结果没有测量性能，没有评估完整真实 TUI；当前资料不足以决定产品长期使用自研核心或哪一个外部核心。

| 选项 | 本轮得到的证据 | 仍需承担或验证的工作 |
|---|---|---|
| 暂留自研 C++ 核心 | 能直接观察全部投影格/历史/样式；可以在 feed 前后接入计量；共同场景与参考一致 | 未支持输入仍终止解析；大量模式/回复/resize 缺失；所有语义、测试和兼容维护由本项目承担；现有字符串格和移动行的实际成本未量化 |
| 通过适配层复用 pyte | 固定源码/许可可获得；ByteStream、HistoryScreen 可无窗口驱动并观察状态；同一套输入和检查点已运行 | 六个边界行为与当前策略不同；需要 Python 运行时和自身适配；尚无产品输入/呈现/生命周期整合或同配置性能证据。不能以其语言推断够快或不够快 |
| 后续适配其他开源产品核心 | 当前 trace 协议、输入和精确差异报告可以复用 | 本轮未构建或测量另一个原生核心；不可声称已完成候选比较。需要固定版本/许可、干净构建、足够模式/回复能力、可观测屏幕/历史和独立计量边界 |

维护负担列为具体缺口，未虚构工时或使用代码行数衡量质量。

## 决定

1. **保留现有核心用于受限实验和 G1 的有限集成，pyte 只作为测试依赖。** 不将这一临时安排升级为长期自研承诺，不发布性能等价声明。
2. 将可替换边界固定在“字节 feed → 可检查状态/变更 → 独立呈现”之间。参考适配不得依赖 GUI；自研核心、传输、呈现分别可测。当前 trace 是测试协议，未来产品状态接口仍需针对一致性/增量更新设计。
3. 共同子集每次变更执行差分；已知差异单独精确检查。错误恢复等不在共同子集的功能先定义行为，再增加负面与差分测试。参考结果与规范或产品策略冲突时保留复现并裁决，不机械追随任何一个实现。
4. C2 可在现有核心上补有界恢复，T1/V1 可继续独立推进。进入完整 TUI 功能扩张前，启动一个可构建的外部核心适配切片，再作产品路线决定。

## 必须重审的关卡

当前关卡对应 R2：扩大终端模式与常用 TUI 的实现投入前，使用同一批字节轨迹至少比较自研和一个实际构建的外部候选；仅有库名或 README 不满足此条件。候选构建与共同子集/历史投影适配可以在 R1 期间并行进行，不要求先把自研核心补成完整终端，也不等待正式 WindTerm 基线。具体补齐：

- 固定候选版本、许可与传递依赖；干净 Windows 构建和自动 headless 运行。
- 复用本轮输入/检查点，增加异常恢复、备用屏、滚动区、resize、查询回复和真实 shell/分页器/编辑器轨迹；解释六类已知差异。
- 独立统计适配层与核心的 CPU、内存/分配、长输出与交互延迟；相同输入/可观察状态/完成端点下重复测量，显示开销单独记录。Python 参考的 trace 运行时间不用于此结论。
- 记录修复一个兼容性失败需要改哪里、可否回馈上游、如何升级和复现回归，以及对当前 transport/presentation 接口的影响。

若 P1 测出自研格/行布局成为主要成本、C2/C3/C4/C5 出现持续难以界定的模式耦合，或外部候选在正确性/维护成本/测量接口上表现更适合，则提前重审。即使最终复用外部核心，本轮原创输入、差分工具和机制实验仍继续保留。

## R2 重审决定（2026-10-25）

完整的平台、维护、兼容修复与接口证据见 [R2 原生核心路线重审](../research/2026-10-25-core-route-review.md)。

1. **R2 新终端能力复用 `alacritty_terminal` 的 `Term` / `Processor`，不再沿自研核心扩展完整 VT/TUI。** 原始比较版本为 0.26.0，当前整合依赖固定为 `0.26.1-dev+termforge.3`。候选的实际备用屏、滚动区、回复、resize、真实应用回放和持续回归优于重新实现这些能力的维护路径；共同 feed 计量没有显示必须因语言或核心吞吐放弃候选。
2. **只复用核心，不锁定候选 PTY/event loop。** 保留现有 ConPTY/传输、OutputQueue/InputQueue 背压、会话生命周期和 UI 所有权。终端 `PtyWrite` 经有界输入队列发送；其他事件按产品合同处理。
3. **保留自研 C++ 核心作为 R1 回退和独立差分参考。** 候选尚未接入产品；只有相同文字、选择、搜索、IME、多会话和资源回归通过后才替换默认会话。#27–#30 可按选定路线实施，#34/#35 的产品与路标验收不变。
4. **产品适配不走全量 JSON 投影。** 使用候选 damage 与拥有所有权的快照；稳定行 ID、版本、软硬换行和淘汰语义由适配器显式维护，不能以行号替代身份。候选 reflow 不得静默替换 #29 的物理行合同。
5. **兼容与依赖修复是整合前置。** `0.26.1-dev+termforge.2` 已落实 ED1/ED2、上游零宽字符内存等修复及稳定行元数据，当前共同矩阵 95 次一致；来源和补丁见[台账](../../experiments/candidates/alacritty/PROVENANCE.md)。C++ 拥有值适配已独立验证，实际输入队列、默认 shell 与 R1/资源回归仍须验收，后续升级继续固定精确 commit，不冒充原始发布版。
6. **平台缺口保持显式。** Windows 7 的 Tier 3 Rust target 和非 ConPTY 后端、macOS 10.13、glibc 2.17、x86/ARM 均未验收。核心路线不把 Ubuntu/Windows headless CI 扩大为完整平台支持。
7. 若稳定身份/增量接口、兼容补丁维护、真实资源预算或必要平台无法满足，重审本决定；不得无记录地回到大规模自研 VT 扩张。现有共同轨迹、fuzz、真实应用和成本工具继续作为升级门槛。
