# ADR-0006：完整复刻目标、Windows 优先与决策确认

- 状态：已确认
- 日期：2026-10-26
- 决策者：项目负责人（用户）
- 确认依据：本次 `$grill-me` 逐项讨论及最终确认“可以的 包括issues等等”。下表记录确认的含义；不将此前 ADR 的状态、提交作者或 issue 关闭解释为用户确认。
- 范围与执行入口：[PLAN](../PLAN.md)、[FEATURES](../FEATURES.md)、[TRACKING](../TRACKING.md)。本文保存决策依据和权限边界，不维护第二份路线或进度表。

## 已确认的方向

| 决策 | 确认内容与依据 |
|---|---|
| 第一目标 | 用户明确“将windterm开源出来”是第一目标。交付完整开源、可独立构建的实现，完整复刻功能、操作行为、界面和性能。 |
| 内部实现 | 用户选择外部行为等价，不强求内部结构一比一，同时要求尽可能研究、借鉴原版代码与关键机制。公开源码复用、逆向研究指导的实现、自主开发及其他开源组件均可作为手段；具体来源仍遵守 [PROVENANCE](../PROVENANCE.md)。 |
| 固定版本 | 用户明确“固定windterm2.7.0”；版本升级另行确认，当前任务不追随最新发行版扩大目标。 |
| 平台与首个完整版本 | 用户明确“最终目标是全平台，但是首要目标是我们的windows”，并确认以 Windows 11 x64 为首个完整版本验收环境。最终覆盖 Windows、Linux、macOS；其他系统版本、最低版本和架构仍需单独明确。 |
| 推进顺序 | 先对齐终端基础能力与性能，再逐步接入 SSH、SFTP 和其余功能。平台可行性及独立调查可并行；Linux/macOS 的完整客户端验收不阻塞首个 Windows 完整版本。 |
| Alacritty | 用户确认“可以保留”。保留已有代码与证据，重新作为待评估候选；比较目标行为、性能及维护成本后，再确认正式核心选型。 |
| 性能标准 | 吞吐、交互/滚动/搜索延迟、CPU、内存/长期增长及多会话关键指标分别达到原版同等水平。用户明确“具体的波动范围需要后续与我明确”；当前没有获得任何数值容差的批准。 |
| 行为裁决 | 用户明确“原版优先”。与通用规范、第三方核心或既有项目策略冲突时，默认以固定原版的实际行为为准；明确缺陷的修正方案另由用户确认。未知目标行为继续调查，不计为匹配。 |
| 决策权限 | 目标范围、主要技术路线、验收门槛和重要差异由用户确认；已确认方向内的研究、逆向调查、候选实验、具体实现、测试和修复由代理自主推进。 |

## 对现有路线的处理

- [ADR-0003](0003-core-reference-and-reuse.md) 的既有 Alacritty 实验及结果保留；2026-10-25 的路线选择不再作为当前正式选型依据。最终决定由 [#34](https://github.com/JavaZeroo/termforge/issues/34)提交证据和方案供用户确认。
- [ADR-0004](0004-presentation-backend.md) 的 Win32/DirectWrite/Direct2D 路线继续作为实验实现，GUI、呈现及产品后端尚未正式选定。
- [ADR-0005](0005-physical-row-resize.md)、字体/网格、字素、选择等现有合同仍用于准确描述实现和防止回归。它们与原版的匹配情况须另验；重要差异不因测试通过或写成合同而自动获准。
- 已完成的构建、实验和限定验收保留原来源、结果和历史状态。当前问题由现有责任 issue 接续；不因方向重审重开全部已关闭任务，也不关闭真实缺口。

## 后续决定如何生效

重大决定先以“提议 / 待用户确认”记录，包含问题、候选及取舍、证据、未测项、影响的目标和后续工作。用户确认后才标为“已确认”，注明日期及确认依据；被替代的结论保留历史标记。实验实现状态与产品决策状态分开记录。

性能工作先建立可靠的原版基线，给出逐场景指标、重复样本、噪声和容差提案，再与用户明确并记录确认。确认后的门槛用于后续验收；不得根据待验结果反填一个刚好能通过的数值。既有诊断、测试超时和资源护栏保留原含义，不自动成为用户认可的 WindTerm 等价标准。

候选比较、证据准备和无依赖的实现工作可以自主继续；将候选正式采用、改变目标范围或接受重要行为差异前，提交具体可审查方案。源码可用、CI 通过、issue 关闭及 ADR 的旧“Accepted”文字均不替代这一步确认。
