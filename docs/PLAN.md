# 总体路线：独立完整复刻 WindTerm 2.7.0

## 目标与固定对照

目标是以完整开源、可维护、可独立构建的实现，复刻官方 WindTerm 2.7.0 的可观察功能、操作行为、界面和性能。用户应能完成相同的工作，而不仅是看到相似布局。完整复刻不要求恢复私有源码；它要求固定目标矩阵中的每一项都具有独立实现和验收证据。

用户已确认上述第一目标及 [ADR-0006](adr/0006-confirmed-project-direction.md) 的决策边界。首个完整版本以 **Windows 11 x64** 为验收环境，最终覆盖 Windows、Linux、macOS。其他系统版本、最低版本和架构列为待明确范围；官方历史支持声明是调查输入，不自动成为首个 Windows 版本的验收承诺。

默认以 WindTerm 2.7.0 的实际行为为准。与通用规范、第三方核心或现有项目策略冲突时，记录原版证据并按原版对齐；明确缺陷的修正方案及重要差异由用户确认。认真研究、借鉴原版公开代码与关键机制，内部结构不要求一致。

主要对照固定为官方 **2.7.0 Windows x64** 发行包，EXE SHA-256 为 `7b10531dccc7cd614ae559f36f1ef518e0c96335637431b4646354823b2804d0`。原安装目录中的不同 EXE 不混入该基准。其他平台、架构及版本的支持范围也必须列入目标矩阵并逐项处理，不能把 Windows 原型或 Linux 核心 CI 当成完整跨平台产品。

官方 `2.7.0` tag 指向提交 `a8336c1d1e3dd1a981500dae8ef9eb42066de95f`。目标清单的公开来源是[固定提交 README](https://github.com/kingToolbox/WindTerm/blob/a8336c1d1e3dd1a981500dae8ef9eb42066de95f/README.md)与[2.7.0 发布说明](https://github.com/kingToolbox/WindTerm/releases/tag/2.7.0)。官方声明、发行物静态事实、实际运行观察和本项目实现结果分别记录，前一类不能替代后一类。

正式产品核心已确认继续自主开发 C++，当前 GUI 路线采用 Qt Widgets，见 [ADR-0008](adr/0008-cpp-core-qt-widgets.md)；Windows 本地 Shell 采用[随包固定微软 ConPTY](adr/0007-bundled-microsoft-conpty.md)。集中整合这一条产品路线，确认不代表新配置的实现或性能已验收。

当前实现与证据以[功能矩阵](FEATURES.md)为准，执行任务以[任务跟踪](TRACKING.md)为准。本文件只维护路标、工作包、依赖和出口条件，不累计每批开发过程。

## 当前站位与下一次交付

**R1 基础文字交互已按限定合同验收，当前推进 R2，尚未达到开发版出口。** 下一次产品交付是在明确支持的 Windows 环境中可靠运行本地 shell 和固定 TUI、恢复工作配置，并提供可复建的开发包。当前各构建配置已做什么见 [FEATURES](FEATURES.md)；R2 的接续顺序、并行工作和出口检查只在 [R2 交付路线与验收](milestones/R2-local-terminal.md)维护，实时进度由 [GitHub 执行项](TRACKING.md)承接。

[平台范围](../research/windterm-2.7.0-platform-scope.md)与 [ADR-0003](adr/0003-core-reference-and-reuse.md)保存已有调查和核心比较。Alacritty 的代码与证据保留为参考，不继续作为正式产品核心扩展；其字素、TUI 与历史结果不能转记到自主 C++ 核心。#34 接续已确认路线的接口、迁移、支持配置与证据收敛，重要原版差异和数值性能容差仍须用户确认；原型或 Alpha 均不代表可日常替代 WindTerm。

“完整复刻”同时包含功能、行为、UI、性能和交付，不能用单一完成比例概括。全量目标台账必须提前建立；性能测量和定向逆向从现在持续进行，远期路标表示验收位置，而不是推迟开始的日期。

## 五个路标

保留五个路标编号，下面从远到近展开；主线优先对齐终端基础能力和性能，再推进 SSH/SFTP 及其余功能。R1 → R2 → R3 → R4 → R5 首先完成 Windows 11 x64；R5 内先验收 Windows 完整版本，再完成 Linux/macOS 扩展和全平台出口。远期只拆功能域，进入执行前再形成可验收的小任务。

| 路标 | 达成后的能力 | 主要验收边界 |
|---|---|---|
| R5 完整 2.7.0 复刻验收 | 先在 Windows 11 x64 完整替代，再扩展 Linux/macOS | Windows 和全平台分别验收全功能、行为、UI、性能及交付；Windows 通过不关闭全平台总项 |
| R4 高级工作流、多协议与性能收敛 | 在 Windows 完成高级文本、自动化、多协议和完整工作区 | Windows 高级功能整合及性能收敛；跨平台可行性调查可提前推进 |
| R3 Windows 远程日常版 | 可靠使用 SSH、文件传输和多会话完成远程工作 | 认证与身份、传输完整性、异常恢复、会话管理及持续运行 |
| R2 可靠本地终端与开发版 | 日常使用本地 shell 和常见 TUI，重启后恢复工作配置 | 终端兼容、复杂文字、实际 DPI、持久化、真实应用与可分发构建 |
| R1 基础文字交互 | 浏览历史、选择复制、粘贴、搜索，并完成基础中文输入 | 文字与输入正确，多个会话隔离，持续输出时仍可操作 |

性能与原版研究贯穿所有路标，终端基础能力及性能是当前优先工作。R3 协议库、受控环境及 Linux/macOS 可行性调查可以提前并行；完整 Linux/macOS 客户端不作为 Windows 完整版本的前置，仍是最终必需交付。

## R5：完整 2.7.0 复刻验收

**用户结果：** 不再需要因目标矩阵中的功能、交互或性能缺口回到 WindTerm 2.7.0；源码、依赖、资源、测试和构建流程均可获得。

分两个出口管理：**先完成 Windows 11 x64 的完整复刻验收**，允许独立交付该平台的完整版本；随后实现和验收 Linux/macOS 客户端及已确认的扩展平台矩阵。Windows 出口通过时，全平台总项仍保持未完成。后续系统版本/架构的范围须由用户明确，不从官方资产清单或当前 CI 环境自动推导。

工作块：

- **功能与行为闭合。** 对固定目标清单逐项验收，包括不在首批日常路径中的设置、菜单、会话状态、错误恢复和边界行为。清理仍为“未知”“仅静态线索”“只有布局”的项目。
- **UI 与操作闭合。** 在固定状态、字体、DPI、窗口尺寸和输入上下文下比较布局与操作结果；覆盖弹窗、面板、工作区、快捷键和持久化后的状态。视觉误差与功能差异分别验收。
- **性能与稳定性闭合。** 在共同功能配置下逐项验证吞吐、交互/滚动/搜索响应、CPU、内存/长期增长、历史规模、传输和多会话公平性；给出原始样本身份、正确性、误差与适用范围。各指标门槛及允许波动范围由用户在可靠基线后确认；未确认或未测项不能计为完整复刻通过。
- **平台与交付闭合。** 首先在 Windows 11 x64 核对完整矩阵、可复建发布、依赖来源和许可、升级/迁移与故障恢复。随后完成 Linux/macOS 的 PTY、输入法、字体、窗口、剪贴板、会话和打包整合及真实客户端验证；按用户确认的系统/架构范围逐平台复验，核心 CI 不代替客户端验收。
- **维护闭合。** 将已确认的参考行为、协议兼容性和性能预算变成持续回归，使后续开发不依赖重新阅读过程记录或个人环境。

**出口条件：** 每个必需矩阵项都有目标依据、实现入口、验证方法和结果，全部达到既定合同。记录了差异不等于消除了差异；缺少环境、未知端点或尚未验证的功能仍是未完成。不得通过减少测试、改变负载、移除功能或静默缩小平台范围宣布完整复刻。确需改变目标时，应明确形成新范围版本，不能用新范围证明原目标已经完成。

## R4：Windows 高级工作流、多协议与性能收敛

**用户结果：** 在 Windows 从日常远程终端扩展到 WindTerm 的完整专业工作流，各面板和动作背后都有真实功能。

工作块：

- **高级连接与协议。** 在固定来源与运行观察确认的范围内补齐高级 SSH 认证、复用、跳转、代理、转发与 SSH signal 请求，以及 Telnet、Raw TCP、串口、X/Y/Zmodem、X11 等能力。每个协议独立验证生命周期、错误和资源边界。
- **文件与远程工作流。** 扩展 SCP、本地/远程文件操作、传输队列和关联操作；明确完整性、覆盖、冲突、取消和重试语义。WSL 文件与系统信息联动按参考版本实际行为验收。
- **高级文本与自动化。** 补齐高亮、折叠、标记/大纲、补全、命令历史、命令面板、Sender、QuickBar、Free Type Mode（用户可见的自由输入模式，具体行为待取证）、同步输入、自动执行及其他已确认的工作流；后台分析必须有预算并可取消。
- **完整工作区。** 完成剩余面板、对话框、模式、主题/颜色、快捷键上下文、多语言、日志及会话操作；分清参考版本支持、参考版本已知限制和本项目额外能力。
- **tmux 深度整合。** 按 2.7.0 的会话、窗口、面板与操作合同实现整合，而不是把“能在终端里运行 tmux”作为完成。参考版本已知不支持的组合不自动升级为本路标必须实现的增强。
- **跨平台准备。** 提前调查 Linux/macOS 的 PTY、输入法、字体、窗口、剪贴板和打包适配，识别影响长期选型的障碍。完整客户端整合与验收在 R5 的 Windows 出口之后完成，不以放弃跨平台换取当前选型便利。
- **性能收敛。** 对大历史、后台搜索、多会话、慢连接、大量小文件及持续输出识别瓶颈，再比较数据布局、缓存、压缩、批处理和调度方案。采用能保持正确性与维护成本的方案，不以恢复 WindTerm 的私有内部结构为前提。

**出口条件：** Windows 的每个声明支持功能域都有可重复集成环境、失败路径、资源回收及真实工作流验证；功能与性能差距集中到明确的最终验收清单。R5 的 Windows 出口核对全矩阵并关闭剩余缺口；Linux/macOS 的整合和验收继续单列，不把其尚未完成视作 Windows 出口失败。

## R3：Windows 远程日常版

**用户结果：** 在 Windows 上管理本地与远程会话，完成连接、命令操作、上传下载、重连和日常故障处理。

| 工作包 | 必须交付的行为 | 主要验收 |
|---|---|---|
| SSH 传输与认证 | 选择维护中的开源组件；完成首批认证方式、连接/取消/超时、输入输出、resize、基础交互中断（如 Ctrl-C）和关闭 | 受控 SSH 服务；正确与错误认证；关闭与断线；传输字节和进程状态；库许可与版本可追溯；SSH signal 请求另归 R4 |
| 主机身份与凭据 | 初次信任、主机密钥变化、凭据保存/读取/删除和不保存路径 | 连接身份不会被忽略；秘密不进入日志/配置明文；测试与故障产物不泄露凭据 |
| 基础网络路径 | 完成日常需要的代理/跳转路径与明确错误提示 | 直连、不可达、超时、代理失败及取消；网络成本与终端处理成本分开 |
| 会话管理 | 本地/SSH 配置、分组/查找、启动参数、重复打开、断开/重连、保存与恢复 | 活动状态和保存配置一致；关闭只影响目标会话；配置损坏与迁移可恢复 |
| SFTP 与文件 UI | 浏览、上传/下载、必要文件操作、队列、进度、覆盖、取消、重试 | 文件哈希与数量正确；批量/大文件/错误路径；部分完成状态明确；操作实际落到受控服务 |
| 多会话与并发 | 终端交互、后台高输出和文件传输并行；面板焦点与目标明确 | 前台输入不被后台任务饿死；有界内存；多会话关闭与退出没有残留 |
| 日常开发版交付 | 扩展安装/便携包、配置迁移、使用说明、问题诊断和持续运行 | 干净环境与固定真实任务；重复连接/关闭/传输；长期资源稳定；来源与许可完整 |

**依赖：** SSH 组件调查、原始字节测试和受控服务可以提前开展；窗口整合依赖本地会话边界，远程 TUI 声明依赖 R2 的核心兼容性。SFTP 集成依赖可验证的 SSH 生命周期。不能把库暴露了接口当成产品功能完成。

**出口条件：** 本地终端、SSH、基础 SFTP、会话工作区和分发包形成完整日常流程，并通过失败恢复、身份/凭据、持续运行及并发验证。高级协议和高级文本尚未完成时仍明确保留在 R4。

| 持久化 | 会话配置、工作区布局、标题/比例等状态的明确保存范围；原子替换、版本迁移、损坏回退 | 新进程恢复与异常配置场景通过；不会把当前仅保存布局说成完整会话恢复 |
| 已定路线的架构与迁移 | 按 ADR-0007/0008 整合自主 C++、Qt Widgets 与固定微软 ConPTY；明确历史/快照、传输/呈现、依赖和维护边界 | #34 保留实现与证据收敛责任；重大替换或重要行为差异另经用户确认，性能容差后续明确 |
| 开发版构建与交付 | 清理实验与产品入口、可分发构建、字体/依赖来源、使用说明、诊断与长时回归 | 干净机器可以构建和使用；功能声明对应可下载产物与真实测试；重复开关会话资源稳定 |

**前置与架构门槛：** [平台切片 #23](https://github.com/JavaZeroo/termforge/issues/23)和[核心比较 #20](https://github.com/JavaZeroo/termforge/issues/20)的限定证据保留为参考；[全量目标台账 #19](https://github.com/JavaZeroo/termforge/issues/19)继续并行调查。#34 按已确认的 [ADR-0007](adr/0007-bundled-microsoft-conpty.md) / [ADR-0008](adr/0008-cpp-core-qt-widgets.md)收敛接口、迁移与证据，不重复申请相同路线；功能验收、重要差异及性能数值门槛仍分别闭合。

**出口条件：** 固定本地真实任务、TUI、文字输入、配置恢复、真实 DPI 和干净环境发布全部通过；实际支持与已知差异进入功能矩阵。详细验收、证据边界与近期执行顺序见 [R2 出口检查表](milestones/R2-local-terminal.md)。仅普通命令可运行不等同于可靠本地终端。

## R1：基础文字交互闭环

**用户结果：** 在主区和底部的真实会话中阅读历史、选择复制、粘贴和搜索，完成基础中文输入；持续输出和切换会话不会破坏这些操作。

详细合同、子任务、依赖与验收见 [R1 基础文字交互](milestones/R1-local-text.md)。本路标的范围为：

- 定向核实参考版本的文字交互、焦点和快捷键行为，形成独立实现合同。
- 历史/屏幕/窗口坐标、历史浏览和跟随输出规则。
- 选择模型、正确 Unicode 复制、明确换行策略和剪贴板入口。
- 有界粘贴、必要的模式协商、取消及会话隔离。
- 基础历史搜索、定位、高亮、取消和淘汰处理。
- 基础 IME 组合/提交/取消与键盘输入闭环；复杂 Unicode、完整字素与广泛字体兼容留到 R2。
- 焦点、重命名框、搜索框、菜单与键盘/鼠标动作的正确路由。
- 多会话、持续输出、resize、DPI/zoom、关闭及资源回收的自动集成验证。

**出口条件：** 用户可完整走通“输入命令 → 阅读历史 → 选择复制 → 粘贴 → 搜索定位”的真实流程；基础中文输入正确，操作不串会话。复制内容与粘贴字节由独立预期校验，画面相似不能替代数据正确。性能记录作为回归护栏，不在此路标提前声明达到 WindTerm 性能。

## 调查与实现如何配合

每个需要复刻的行为采用同一条链路：**逆向/观察 → 行为合同 → 独立实现 → 差分验收**。

1. 先提出具体问题和合成场景。优先公开文档、许可明确的源码、发行物声明与运行时行为；需要时再做定向二进制调查。
2. 将观察转成输入、状态、动作、结果和边界的合同，分别标记事实、推断、未知与本项目设计选择。静态符号不能代替运行结果。
3. 研究、借鉴许可明确的原版源码和关键机制，选择独立实现或开源组件。协议、核心状态、历史、会话与呈现应可分别测试；不复制私有源码、资源或未授权资产。参考规范用于理解行为，冲突时仍以固定原版为默认依据，明确缺陷的修正另由用户确认。
4. 对相同场景比较状态、文字、几何、动作结果或协议数据，再进行视觉检查。没有参考运行证据的项仍标未知，不用本项目自身测试补成“参考匹配”。
5. 发布精简事实、原创探针与可公开结果；原始二进制、私有提取物及敏感数据留在受控本地。具体规则见 [PROVENANCE](PROVENANCE.md)。

逆向服务于明确的行为或性能问题，不是启动任何工程任务前都必须完成的全程序反编译。不能改变规格、解释测量或支持设计选择的调查分支应结束，保留问题再推进可独立完成的工作。

## 自动执行与性能要求

按照 [ADR-0002](adr/0002-automation-first-investigation.md)，默认由工具完成构建、受控服务准备、测试会话、输入驱动、采样、失败记录与清理。所有实验有超时和资源回收，不把自动化缺口变成要求用户反复点击、输入确认或跑命令的流程。

真实显示器、外部服务或平台暂不可用时，建立自动探针和明确的验收缺口，继续独立任务；不能把模拟场景当真实环境通过，也不能让一个环境缺口阻塞全部工作。

性能工程从 R1 开始，而非 R4 才开始：

- [观测工具 #3](https://github.com/JavaZeroo/termforge/issues/3)继续承担自动 WindTerm 适配、观测开销校准及完整运行记录 JSON Schema；[正式基线 #4](https://github.com/JavaZeroo/termforge/issues/4)承担节流/终端交互驱动、同配置重复批次、无插桩对照与严格环境控制。两者归入 R4 收敛验收，但可独立提前推进，不作为 R1 全部工作的前置。

- 先保证数据、屏幕和工作流正确，再谈优化；不能丢输出、改变必要功能或积压呈现换取吞吐。
- 固定负载、版本、环境、功能配置和完成端点，记录原始样本、重复结果、波动、工具扰动及限制。
- 分开接收、解析/状态、历史、布局/绘制、提交与实际呈现；未知端点保留未知。
- 同时覆盖吞吐、交互延迟、CPU、内存、长期增长和多会话公平性。一个数字不能代表整体达标。
- 自动 WindTerm 对照尚不能成立时，继续自有成本分层和回归，但不能据此宣布已经追平。
- 在可靠原版基线和共同功能范围明确后提出逐场景预算及允许波动范围，与用户明确并记录确认后用于验收；当前没有批准任何数值容差。采样波动、既有诊断护栏和候选间回归数字不自动成为等价标准，不能根据待验结果反填门槛。
- 按测量瓶颈选择优化；不预设 C++、某个 GUI 框架或恢复同样内部结构就必然达到同样性能。阶段版本如实报告差距，完整复刻必须满足用户确认的各项门槛。
