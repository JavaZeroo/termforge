# 接收机制实验：首轮自动闭环

> 本文的“下一步”和工作包状态属于该历史批次。当前能力见 [FEATURES](../FEATURES.md)，剩余归因与性能任务见 [TRACKING](../TRACKING.md)；原始测量数据保持不变。

2026-10-22，在 Windows 11 build 26200、Intel Core i7-9700（8 核 / 8 逻辑处理器）上，使用 MSVC 19.42.34433、Windows SDK 10.0.26100、x64 Release /O2 构建。不是隔离机器；未固定 CPU 亲和性、电源计划或系统后台负载。

[源码与协议](../../experiments/receive/README.md)；[完整样本](../../experiments/receive/results/2026-10-22/samples.jsonl)；[汇总](../../experiments/receive/results/2026-10-22/summary.json)；[身份记录](../../experiments/receive/results/2026-10-22/manifest.json)。只发布自有合成数据，不含 WindTerm 二进制、私有配置或反编译输出。

## 已验证

- 共 120 次运行：24 次紧容量正确性验证、24 次预热、72 次测量。所有字节内容、顺序、总数及队列上限检查通过，没有出现本次可观测的丢数据或超时。
- 紧容量正确性场景中 22/24 次实际触发背压等待，最多 256 次；均正确处理非整块 EOF。有限测试不证明所有调度都安全。
- stream、burst、slow、yield 各组合均完成。独立负面校验及原生参数守卫共 5 项测试通过。
- 通知合并减少了 `notify_one` 调用；这不是实际线程唤醒次数，更不是 Qt 信号事件计数。

## 持续输出观察

同一 8 MiB 输入，以下各组 3 次测量；吞吐为中位数及最小–最大值。通知、读取数和每次运行队列延迟 p95 均取运行间中位数。

| 读取上限 | 通知策略 | MiB/s 中位数（范围） | 读取数 | 通知数 | 队列到校验 p95，us |
|---|---|---:|---:|---:|---:|
| 512 B | 每批 | 291.2（253.5–424.2） | 16,384 | 16,384 | 66.0 |
| 512 B | 空→非空 | 343.6（299.4–353.9） | 16,384 | 7,624 | 32.8 |
| 4 KiB | 每批 | 721.8（688.8–898.3） | 2,048 | 2,048 | 30.2 |
| 4 KiB | 空→非空 | 827.8（623.6–1,107.9） | 2,048 | 999 | 26.6 |
| 64 KiB | 每批 | 927.8（617.6–1,102.9） | 184 | 184 | 74.3 |
| 64 KiB | 空→非空 | 1,134.2（961.6–1,142.1） | 194 | 127 | 58.0 |

较大的读取上限在本实验中伴随更少的读取调用；64 KiB 不是每次实际返回量，同组读取数也会随调度变化。吞吐与队列延迟没有呈现同样的单调变化。两种通知策略的区间有重叠，不能把三次运行的中位数差直接解释成稳定收益。

CPU 原始值保留在样本中，出现 15.625 ms 台阶和 0 ms：样本只有数毫秒到数十毫秒，当前计量精度不足以支持 CPU 优劣结论，**0 不代表没有消耗 CPU**。本轮不发布 CPU 节省比例。

全部模式的进程峰值工作集约 4.63–12.86 MiB；各模式输入 fixture 大小不同，不可直接横向比较。它包含输入、分配容量、延迟记录和线程成本，不能归结为队列本身。

## 压力场景与限制

slow 模式每块请求休眠 100 us，实际 Windows 调度使部分运行的队列到校验 p95 达到约 7.59 秒。它验证积压下完成消费，不是终端延迟预算或实现目标。测量阶段 slow 输入本身只有 256 KiB、等于队列上限，未触发背压；背压证据来自独立紧容量场景，不能混为一谈。

这次没有解析器、屏幕、历史、绘制、真实 ConPTY 或 SSH。延迟端点排除了生产、管道和等待队列空间的时间；条件变量通知不代表完整事件循环。逐块分配、时间采样和内容比较均在热路径中。当前结果不能用于宣称达到 WindTerm 性能，也不用于锁定完整技术栈。

## 决策与下一步

保留读取上限和通知策略为可调参数，不指定“64 KiB 永远最好”。下一步接入最小解析/屏幕状态回放，让消费端执行可验证的实际工作；随后增加持续时间足够长的计量、端到端等待端点及多会话公平性实验，重新比较吞吐与响应延迟。正式 CPU 比较前需要延长计量区间并验证观测精度。

ADR-0002 的 B 工作包只完成接收机制子实验；完整核心规格、解析状态回放及 C 自动 WindTerm 会话仍未完成。
