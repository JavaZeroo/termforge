# R2 性能预算：回归型规则

状态：回归型治理方向由 ADR-0009 决策 3C 记录；**数值容差尚未获批，门禁未启用**。本文旧版将 20% 和 5 次中位数写成已确认规则，但未列出数值确认依据，与 AGENTS.md / ADR-0006 冲突；本次恢复为待确认提案，不改变既有测量或诊断期限。

## 为什么不是绝对值

- 目前只有诊断样本（启动 p50/p95、字素吞吐、repaint 批量、`resource_settle_ms`），没有在受控环境下复现的基线；
- 尚无满足同负载、同正确性与完成端点要求的正式 WindTerm 对照，不能从内部计时或局部吞吐推导性能等价；
- R2 先建立可重复的回归证据；绝对目标和原版等价标准由后续可靠基线及用户确认决定。

## 待确认的执行提案

1. **基线**：每个受监控的测量项有一个"已记录基线"，来源必须是一次可复现的 CI 运行（带 run id 与 commit）；
2. **判定**：旧稿提出“相对基线变差超过 20%”；这个数值只保留为待讨论提案，不能用于宣布通过/失败。取得同负载、同正确性和受控重复基线后，与用户逐项明确容差；
3. **噪声处理**：旧稿提出同一作业重复 5 次取中位数。先核对实际波动、环境和观察开销，再冻结样本方法；不得为取得通过临时增加重复次数；
4. **诊断守卫独立**：既有的诊断阈值（如 10 秒夹具期限）不受本文约束，仍按各自 issue 的合同执行；
5. **基线更新**：只有确认"变更是预期的"（例如功能修复带来的额外工作）才能更新基线，并在 PR 里写明理由。

## 受监控项（初始集合）

| 测量项 | 来源 | 备注 |
|---|---|---|
| 启动耗时（p50/p95） | `windows-2025-startup-latency` | 已有结果目录 `research/ui/results/2026-10-30-hosted-startup-latency/` |
| 字素吞吐 | 核心测量目标 | 单位与工作负载必须随结果一起记录 |
| repaint 批量与消费耗时 | `TERMFORGE_OUTPUT_TRACE` 分析 | 只看相对变化 |
| `resource_settle_ms` | conpty 探针 | 用于捕捉资源回收变慢 |

## 不属于本文的范围

- 不设定"日常使用流畅"之类的体验结论；
- 不设定与 WindTerm 对比的指标；
- 不覆盖内存占用的绝对上限（另需专项证据）。

## 边界

- 20% 不是已确认的回归容忍带，也不是性能目标值；
- 基线噪声尚不能可靠区分变更成本时，应先稳定测量方式；未知保持未知。R2 不以 WindTerm 性能等价或绝对预算为出口，仍需随产物记录已有测量、适用配置和局限。
