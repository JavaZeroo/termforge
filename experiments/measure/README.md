# 核心成本初步探针（P1 未完成）

`core_measure` 使用原创固定输入与独立状态检查，开始把短时回放改为可重复的长批次。它尚未完成分层归因和观测扰动校准，不能用于判断 WindTerm 性能差距或选择最优块长。

```powershell
# 先按 CONTRIBUTING.md 从仓库根目录构建。
python experiments/measure/run.py --bin-dir build/bin/Release --out local/experiments/core-cost-new
```

Linux 单配置构建使用 `build/bin`。输出目录必须不存在；子进程限时 90 秒，内部限时 60 秒。失败记录与 manifest 保留。

## 输入与测量边界

- 固定 1,000 行，每行 76 个 `x` 加 CR/LF，共 78,000 字节；24×80 屏幕、100 行历史。输入在计时前准备。
- `parse` 路径按 512/4096/65536 字节块 feed；`state` 路径直接执行相同字符、移动和滚动操作。后者是另一条调用路径，不能把两者时间相减当成解析器净成本。
- 先预热；每轮计时包含 Parser 构造和解析/状态变更，排除析构、独立格位检查与 JSON 摘要。直到累计测得的 CPU 与墙钟工作时间均达到门槛（默认 1 秒）。每轮检查屏幕、历史、淘汰数、样式和完整状态摘要。
- 8 种配置按固定随机种子交错运行，每种重复 3 次；分配计数开/关分开记录。两种模式都使用同一个替换 `new` 的程序，关闭计数不是无插桩产品基线。
- `ordinary_allocations` / `ordinary_allocated_bytes` 是计时区间内普通 C++ new/new[] 的累计请求次数/字节，不包括对齐分配、C/runtime 分配，不是当前存活内存。Windows 的 peak working set 是整个进程峰值，包含准备和检查；Linux 暂为 null。
- 接收和呈现未进入此探针，保留 null。屏幕更新与历史维护仍混合；当前只覆盖 ASCII 滚动负载。

## 首轮结果与未解决问题

2026-10-22，Windows 11 build 26200、i7-9700、MSVC 19.42.34433 x64 Release：24 个样本全部通过独立状态检查和累计 CPU 门槛；[身份](results/2026-10-22/manifest.json)、[原始样本](results/2026-10-22/samples.jsonl)。结果仅含自生成数据、代码哈希与公共环境信息。

开启计数的所有配置均为每轮 1,137 次普通分配、累计请求 4,533,686 字节。这提供了后续比较数据布局的诊断入口，尚不能定位分配来源或证明其主导总耗时。

同配置 CPU/字节样本波动明显（例如 parse/4096/计数关闭约 33.74–56.98 ns/byte），且本轮开发机同时有构建与测试活动。Windows CPU 时钟的离散粒度仍会影响各短轮次的归属；累加到 1 秒并没有自动证明计量无偏。当前不发布速度排名或计数开销百分比。

P1 剩余：连续长区间与空测量校准，独立第二批次、受控环境、解码/状态/历史的可解释边界、Unicode 和历史规模负载、轻量诊断与无插桩基线比较。只有这些完成后才进入数据结构优化决策。
