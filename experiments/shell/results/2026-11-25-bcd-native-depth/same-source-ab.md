# 同源 ConPTY 缓冲深度实验

用固定 Microsoft Terminal 源码构建基线与候选。候选在两处设置原生视口的路径中保留主缓冲已有高度。两个构建的 `conpty.dll` 哈希相同，`OpenConsole.exe` 哈希不同。官方固定包、同源基线和候选使用同一 Qt 测试源码、工具链与 Windows runner 镜像。首轮在应用补丁时因 CRLF 上下文失败，第二轮按上游原始换行格式构建成功。 [构建](https://github.com/JavaZeroo/termforge/actions/runs/45540116248) · [候选源码](https://github.com/JavaZeroo/termforge/blob/07f971b3a5903039e7d1eee9bf11c8ac9664c603/experiments/conpty/upstream/r29-native-depth.patch) · [运行矩阵](https://github.com/JavaZeroo/termforge/actions/runs/45540912138)

## 字符保留和后续写入

坐标零基，来自原生缓冲。`80×24 → 60×12 → 80×24`。写入阶段由同一子进程发送 `CUP 12;1` 和 `RESIZED`。四阶段探针同时核对真实应用 DSR、Qt 源位置与可见行。

| 变体 | 缩小后、写入前 | 后续写入 | 恢复后 |
|---|---|---|---|
| 官方固定包、同源基线 | 原生缓冲和视口均为 `60×12`，`D(11,0)` | `RESIZED(11,0)` 覆盖旧 `D` | `D` 仍缺，`RESIZED(9,0)` |
| 同源候选 | 原生缓冲 `60×24`、视口 `60×12`，`D(12,0)` 位于视口下方 | `RESIZED(11,0)` 与旧 `C(11,19)` 位于同一原生行，`D` 保留 | `D(10,0)` 已恢复，`RESIZED(9,60)` 随 `C` 的逻辑行回卷 |

在各变体的独立深度对照里，应用把初始缓冲设为 `80×3000`。官方包和基线在第一次缩小时将缓冲收至 `60×12`，候选保持 `60×3000`，保留与覆盖分别复现。候选四阶段仍满足同输入 Telnet 的 Qt 断言。恢复后 Qt 保留源中的 `RESIZED` 位于 `(11,0)`，候选原生为 `(9,60)`。 [逐阶段内容](same-source-ab.json)

## 旧六阶段回归

三个变体都以退出码 1 结束原来的 `--resize`。监督器确认各次均未超时且 Job 剩余进程为 0。第 6 阶段三个变体原生第 11 行均是 `RESIZED` + 12 空格 + `CD`，Qt 核心源第 11 行均为 `RESIZED`。候选的原生缓冲高度为 24，触发额外的旧几何断言。四阶段探针的退出码 0 对应其自身断言。

用 WindTerm 随附的 WinPTY 二进制做了独立六阶段对照。逐阶段子进程源字节与 `--resize` 一致。第 6 阶段实际视口为 `60×12`，原生第 8 行为 19 空格 + `B`，第 11 行也为 `RESIZED` + 12 空格 + `CD`。子进程自然退出 37，外层 Job 剩余进程为 0。 [六阶段 WinPTY 对照](winpty-legacy.json)

Windows 11 x64 QEMU 来宾中的原版 WindTerm 2.7.0 本地 Shell 也完成同样六阶段。先校准独立子进程的视口和实际窗口，窗口像素为 `1228×875 → 988×545`。第 6 阶段实际视口与 UI 容量均为 12 行。原版可见矩形换算得到 `B(8,19)`、`RESIZED(11,0)`、`C(11,19)` 和 `D(11,20)`，与同次原生网格位置一致。原版文档第 20 行的字面内容是 `RESIZED` + 12 空格 + `CD`。前两次均停在几何校准，第三次使用子进程报告的真实网格完成，三次均验证回收。这批记录核对原版公开文本、可见矩形与原生控制台，物理呈现未观测。 [WindTerm 本地 Shell 观测](windterm-local-legacy.json)

同源对照证明了把缓冲高度压到视口高度会导致这个四阶段样本中的旧字符丢失。保留深度后，原生绝对寻址与 Qt 源行的差异依然可复现。后续验证应覆盖原生写入和读取的地址映射，以及 resize 后的 Win32 缓冲尺寸和事件。

## 同源映射接口与额外原版对照

同一固定 Microsoft 源提交构建的修订版在 resize 时报告实际执行的两次网格复制。报告通过同一输出流传递，由 Qt 在独立观察入口核对。六阶段样本中，`B(7,79) → (8,19)`、`C(9,79) → (11,19)`、`D(10,0) → (11,20)` 均与子进程原生读回相符。官方包与修订版均通过三个尺寸的 Win32 光标、文字写入、矩形读写与扩展查询。该轮验证范围是映射接口与独立 Win32 读写，旧 `--resize` 的核心同步断言仍退出 1。 [同源构建](https://github.com/JavaZeroo/termforge/actions/runs/45560850010) · [Windows 对照](https://github.com/JavaZeroo/termforge/actions/runs/45561963694) · [验证数据](ordered-map-validation.json)

原版 WindTerm 本地 Shell 另完成两轮固定输入。六阶段只缩宽时，`60×24` 的原版可见第 12 行仍是 `RESIZED` + 12 空格 + `CD`。四阶段分别定位 `C` 和 `D` 的输入中，原版缩小后可见 `CD` 同行，后续 `RESIZED` 写到单独的一行。恢复后 `D` 与 `RESIZED` 都仍可读。两轮都同时核对真实子进程网格和 UI 文档，证据包含逐阶段原始合成字节和像素矩形。 [本地 Shell 补充样本](ordered-map-validation.json)
