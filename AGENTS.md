# Working on TermForge

- Read README.md, docs/PLAN.md, docs/FEATURES.md and the active milestone before making architecture decisions.
- Follow docs/adr/0006-confirmed-project-direction.md: fully recreate WindTerm 2.7.0, with Windows 11 x64 as the first complete-version target and Windows/Linux/macOS as the final platform goal. Prioritize terminal foundations and performance before SSH/SFTP and the remaining features.
- Follow docs/adr/0008-cpp-core-qt-widgets.md: the confirmed product core is independently developed C++, and Qt Widgets is the current GUI route. Keep investigating the original code and mechanisms; internal implementation need not be identical. Preserve Alacritty code and evidence for reference/differential work rather than expanding it as the product core.
- Follow docs/adr/0007-bundled-microsoft-conpty.md: the confirmed Windows local-shell product route bundles a fixed Microsoft ConPTY. Consolidate existing integration into this route; system ConPTY and WinPTY are diagnostic references rather than parallel product routes. Route confirmation is not implementation acceptance.
- Default to observed WindTerm 2.7.0 behavior when it conflicts with standards, third-party behavior or existing project policy. Unknown behavior requires investigation; important deviations and original-bug fixes require user confirmation.
- The user confirms scope changes, major architecture/dependency choices, acceptance criteria and important behavior differences. Agents may autonomously research, experiment, implement, test and fix within confirmed scope. Record proposal/confirmed status and confirmation evidence in ADRs and issues; merged code or closed issues do not imply user approval.
- Performance tolerances have no approved numeric values yet. Propose them from reliable baseline evidence and explicitly agree them with the user before using them for acceptance; keep existing diagnostic guards separate.
- The project has a limited Windows local-shell prototype. Do not claim a daily-use release, Linux/macOS client, complete WindTerm parity or measured performance equivalence.
- Implement the user-confirmed route in small, measurable slices. Do not add a large application skeleton or claim that the selected stack meets performance targets before benchmark evidence supports it.
- Every performance claim needs workload identity, environment, correctness checks, raw samples and limitations.
- Separate observed facts, hypotheses and design decisions. Static symbols do not prove runtime behavior.
- Keep parser/screen state, history, transport and presentation independently testable in later implementation.
- Preserve terminal correctness and interactive latency while optimizing throughput or memory.
- Do not commit proprietary WindTerm artifacts, resources, private sessions, credentials, crash dumps or raw binary extraction dumps.
- Keep benchmark data local until reviewed for provenance and privacy. Publish synthetic workloads and sanitized results.
- Prefer focused changes with validation appropriate to the work. Do not invent measurements or percentage-complete estimates.
- Keep the roadmap and known differences current when scope changes.
- Follow docs/adr/0002-automation-first-investigation.md: prefer unattended CLI/test workflows; do not turn automation blockers into repeated user clicks, commands or per-run confirmations. Preserve unresolved evidence gaps and continue independent investigation/prototype work.
- R1–R5 in docs/PLAN.md are the current product milestones. Legacy M0–M4 and G1–G3 names appear only in historical evidence. Investigation and independently testable implementation may proceed in parallel; a complete baseline is required for supported performance claims.
- docs/FEATURES.md owns current capabilities and limits; docs/PLAN.md owns milestone scope; the active milestone owns acceptance contracts; GitHub issues own execution status and blockers. Do not append batch diaries to current planning documents.
- Keep build configurations separate in claims: the C++/Qt/fixed-ConPTY product route, legacy default/system build, Alacritty reference build and earlier backend experiments need their own source and validation identity. Do not combine their independent successes into a joint acceptance result or transfer candidate capabilities to the C++ core.
- Source comments explain responsibilities, invariants and policy. Put changing status, batch names and future work in the owning issue; retain fixed experiment/protocol identities when they define behavior or evidence. A TODO must point to a current task rather than duplicate the roadmap.
- Start only an issue whose real blockers are resolved. Record source observations separately from TermForge policies, implement independently, and validate the complete user-visible behavior. An unknown target behavior is an investigation item, not a passed comparison.
- ADR-0003/0004 preserve historical comparison and Win32 presentation evidence; ADR-0007/0008 record the current user-confirmed routes. Substantial replacements, new major dependencies or important behavior deviations need a concrete evidence-backed proposal and user confirmation. Existing experimental success does not establish product acceptance.
- Documentation is primarily Chinese; technical identifiers and concise English summaries are welcome.
