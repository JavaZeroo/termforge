# 官方 WindTerm 2.7.0 首次生产端烟测

用户在隔离测试实例的本地 Shell 中手动运行入口；结果确认真实 WindTerm 下的播放器和资源采样链路已接通。**这不是 T01 性能基线，也没有测到呈现完成时间。**

## 核验结果

- 官方 Windows x64 EXE SHA-256 与准备器固定值一致。
- 固定种子伪随机 ASCII，100 条记录，加结束标记共 7,732 字节。manifest、payload 文件、run 和 producer 记录的字节数/哈希一致。
- 播放器正常退出（0），完整写入 7,732 字节，stderr 为空。
- 生产端计时为 824,300 ns（0.8243 ms）；只表示继承 stdout 的写入返回，不表示解析、画面完成或输入延迟。小负载与单次样本不适合推导终端吞吐。
- 7 个资源样本；首末样本跨度 598,150,800 ns。重新运行资源语义校验器，结果与保存的汇总一致。跳过 tick、发现错误和不可用进程行均为 0；轮询仍可能完全漏掉短命进程。

## 证据与限制

[summary.json](summary.json) 保留应用和工作负载身份、生产时间、资源统计、原始证据哈希。公开记录去掉 PID、进程创建时间、本机路径及绝对时钟计数；原始记录留在 gitignore 的本地结果目录，未公开。

资源窗口覆盖启动及输出后的观察时间，不等于生产端计时窗口。进程树可能包含多个 Shell 和辅助进程；不能将 descendant 的资源解释为纯终端开销，sampler 与 descendant 也不能再次相加。

实际 C0 设置尚未验证；完整文本、布局与最终画面尚未独立核验。`correctness_status` 保持 `not_checked`，消费/呈现端点保持 `null`，性能门槛保持 `not_evaluated`。用户的运行完成反馈不自动视为画面正确性证据。

用户最初只注意到 `TermForge diagnostic: producer_complete`，回看现有输出后明确确认看到了完整的 `TERMFORGE-END ascii 0000000100`。可见标记记录更新为 `confirmed_by_operator`。这是同一次运行的人工确认，不新增成功样本，也不产生呈现时间戳；完整文本正确性仍未验证。

下一步核对实际 C0 设置，再按协议执行 8 MiB T01 交错 on/off 采样开销校准。烟测不能代替预热、重复、稳定等待或独立批次。
